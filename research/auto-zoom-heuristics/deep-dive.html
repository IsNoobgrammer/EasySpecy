Option A: FFmpeg zoompan Filter (NOT Recommended)

How it works

FFmpeg's zoompan filter uses expression-based parameters evaluated per-frame:

ffmpeg -i input.mp4 -vf "zoompan=z='if(between(in_time,5,8),2,1)':d=1:x='iw/2-(iw/zoom/2)':y='ih/2-(ih/zoom/2)':s=1920x1080" output.mp4

Why it fails for dynamic auto-zoom:

  • Expression limitations: x/y/z are expressions evaluated per-frame, but they can only reference built-in variables (in, on, zoom, pzoom, etc.) — NOT external data files or cursor positions.
  • No external data input: You can't feed a file of per-frame coordinates into zoompan. The sendcmd filter exists but only works with a limited set of filters and can't update zoompan dynamically.
  • Designed for images: zoompan was built for Ken Burns effect on still images (d=duration per image). Using d=1 on video works but is hacky.
  • No spring physics: You'd have to pre-compute all spring positions and encode them as massive if/else expression chains — impractical for 30fps × 60s = 1800 frames.
  • Quality issues: zoompan does its own scaling which may not match your output quality settings.

Option B: FFmpeg crop+scale Filter Chain (Viable for Simple Cases)

How it works

Generate a complex filter chain with per-segment crop coordinates:

# For each zoom region, split the video and apply different crops
ffmpeg -i input.mp4 -filter_complex "
  [0:v]split=3[v1][v2][v3];
  [v1]trim=0:5,setpts=PTS-STARTPTS[seg1];
  [v2]trim=5:8,setpts=PTS-STARTPTS,crop=960:540:480:270,scale=1920:1080[seg2];
  [v3]trim=8:end,setpts=PTS-STARTPTS[seg3];
  [seg1][seg2][seg3]concat=n=3:v=1:a=0[out]
" -map "[out]" output.mp4

Limitations:

  • No smooth transitions: Crop jumps instantly between segments. No spring physics possible.
  • Complex filter graphs: 20 zoom regions = 40+ filter nodes. Gets unwieldy.
  • Can't compose with cursor trail: Your cursor trail needs to be rendered AFTER the zoom crop, but FFmpeg can't interleave your Rust rendering with its filter chain.

Verdict: Only viable if you DON'T need smooth transitions and DON'T render cursor trail. Not suitable for EasySpecy.

Option C: Custom Rust Rendering Pipeline (RECOMMENDED)

How it works

Your existing pipeline already does per-frame rendering. Add crop+scale as a transform step:

// Per-frame rendering (pseudocode matching your existing architecture)
fn render_frame(
    source_frame: &[u8],       // raw pixels from captured video
    frame_index: usize,
    zoom_state: &SpringCamera, // pre-computed for this frame
    cursor_trail: &TrailData,
    click_effects: &ClickData,
    output_size: (u32, u32),
) -> Vec<u8> {
    // 1. Get crop rect from spring camera state
    let crop = zoom_state.get_crop_rect(source_size);
    
    // 2. Crop source frame (just pointer arithmetic — zero-copy)
    let cropped = crop_pixels(source_frame, source_size, &crop);
    
    // 3. Scale to output resolution (Lanczos for quality)
    let scaled = resize_lanczos(&cropped, crop.size(), output_size);
    
    // 4. Transform cursor trail coordinates to zoomed viewport
    let transformed_trail = cursor_trail.transform_to_viewport(&crop, output_size);
    
    // 5. Render cursor trail on scaled frame
    render_trail(&mut scaled, &transformed_trail);
    
    // 6. Render click effects (also transformed)
    render_clicks(&mut scaled, &click_effects.transform_to_viewport(&crop, output_size));
    
    scaled
}

Why this is the right choice for EasySpecy:

  • Fits existing architecture: Same rayon parallel batch rendering you already use for cursor trail.
  • Full control over smoothing: Spring physics, custom easing, any interpolation you want.
  • Composable with other effects: Cursor trail, click effects, and zoom all render in the correct order.
  • Performance: Crop is O(1), scale is the only expensive op — and you can use SIMD (packed_simd) or delegate to image crate's optimized resizer.
  • Quality: You control the resampling algorithm (Lanczos3 for best quality, bilinear for speed).

Coordinate Transformation Math

When zoomed, all overlay coordinates must be remapped

/// Transform a screen-space coordinate to the zoomed viewport
fn screen_to_viewport(
    screen_pos: (f64, f64),
    crop_rect: &Rect,       // the crop applied to source frame
    output_size: (u32, u32), // final output resolution
) -> Option<(f64, f64)> {
    // Check if point is within the crop region
    let local_x = screen_pos.0 - crop_rect.x as f64;
    let local_y = screen_pos.1 - crop_rect.y as f64;
    
    if local_x < 0.0 || local_x >= crop_rect.width as f64 
       || local_y < 0.0 || local_y >= crop_rect.height as f64 {
        return None; // cursor is outside zoomed viewport
    }
    
    // Scale to output resolution
    let scale_x = output_size.0 as f64 / crop_rect.width as f64;
    let scale_y = output_size.1 as f64 / crop_rect.height as f64;
    
    Some((local_x * scale_x, local_y * scale_y))
}

/// When cursor is outside viewport, clamp to edge (optional: show arrow indicator)
fn clamp_to_viewport(
    screen_pos: (f64, f64),
    crop_rect: &Rect,
    output_size: (u32, u32),
) -> (f64, f64) {
    let local_x = (screen_pos.0 - crop_rect.x as f64)
        .max(0.0).min(crop_rect.width as f64 - 1.0);
    let local_y = (screen_pos.1 - crop_rect.y as f64)
        .max(0.0).min(crop_rect.height as f64 - 1.0);
    
    let scale_x = output_size.0 as f64 / crop_rect.width as f64;
    let scale_y = output_size.1 as f64 / crop_rect.height as f64;
    
    (local_x * scale_x, local_y * scale_y)
}

Spring Physics Parameters — Tuning Guide

FeelStiffnessDampingUse Case
Snappy (Screen Studio-like)30030Quick demos, fast-paced content
Smooth (Default recommended)17026Tutorials, walkthroughs
Cinematic (Slow, dramatic)8020Product showcases, marketing
Gentle (Minimal overshoot)12035Accessibility, motion-sensitive viewers

Higher stiffness = faster response. Higher damping = less oscillation/overshoot. The ratio stiffness/damping determines the character of the motion.

Edge Cases to Handle

  • Cursor leaves viewport during zoom: Either pan camera to follow (Screenize follow-mode) or let cursor exit and show at edge (Retina approach).
  • Multiple monitors: Zoom coordinates must be relative to the captured monitor, not absolute screen space.
  • Window resize during recording: Window bounds change — use the bounds at the time of the click, not current bounds.
  • Rapid window switching (Alt+Tab): Don't zoom on every Alt+Tab. Require >2s dwell before triggering window-focus zoom.
  • Full-screen apps: If active window IS the full screen, zoom level would be 1x (no zoom). Skip these.
  • Taskbar/Start menu clicks: These are transient — don't zoom to taskbar. Filter by window class or position.
